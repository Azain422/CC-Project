Language Reference Manual and Complete Compiler Design

This document formalizes the mini C-like language and explains the full compiler pipeline, from source text to target output. It also records team reflections, engineering decisions, and project outcomes after end-to-end implementation and testing.

4. Language Reference Manual

4.1 Core Language Definition

Keywords int float bool void if else while for return func true false
Data Types int: 32-bit signed integer
float: decimal floating-point number
bool: boolean value true or false
void: function return type without value
Arithmetic Operators + - * / %
Relational and Logical Operators Relational: == != < > <= >=
Logical: && || !

4.2 Syntax Rules

  • Each statement ends with ;, except block delimiters { }.
  • Identifiers follow pattern: letter or underscore, followed by letters, digits, or underscore.
  • Variables must be declared before use within a visible scope.
  • Function definitions begin with func, include return type, name, parameters, and block body.
  • Expressions respect precedence: unary, multiplicative, additive, relational, equality, logical and/or.

4.3 EBNF Grammar

Program        = { Declaration } ;
Declaration    = VarDecl | FuncDecl | Statement ;
VarDecl        = Type Identifier [ "=" Expression ] ";" ;
Type           = "int" | "float" | "bool" | "void" ;

FuncDecl       = "func" Type Identifier "(" [ ParamList ] ")" Block ;
ParamList      = Param { "," Param } ;
Param          = Type Identifier ;

Block          = "{" { Statement } "}" ;
Statement      = VarDecl
               | AssignStmt
               | IfStmt
               | WhileStmt
               | ForStmt
               | ReturnStmt
               | ExprStmt
               | Block ;

AssignStmt     = Identifier "=" Expression ";" ;
IfStmt         = "if" "(" Expression ")" Statement [ "else" Statement ] ;
WhileStmt      = "while" "(" Expression ")" Statement ;
ForStmt        = "for" "(" [AssignStmtNoSemi] ";" [Expression] ";" [AssignStmtNoSemi] ")" Statement ;
ReturnStmt     = "return" [ Expression ] ";" ;
ExprStmt       = Expression ";" ;
AssignStmtNoSemi = Identifier "=" Expression ;

Expression     = LogicalOr ;
LogicalOr      = LogicalAnd { "||" LogicalAnd } ;
LogicalAnd     = Equality { "&&" Equality } ;
Equality       = Relational { ("==" | "!=") Relational } ;
Relational     = Additive { ("<" | ">" | "<=" | ">=") Additive } ;
Additive       = Multiplicative { ("+" | "-") Multiplicative } ;
Multiplicative = Unary { ("*" | "/" | "%") Unary } ;
Unary          = ["!" | "-"] Primary ;
Primary        = Number | Boolean | Identifier | CallExpr | "(" Expression ")" ;
CallExpr       = Identifier "(" [ ArgList ] ")" ;
ArgList        = Expression { "," Expression } ;

Identifier     = letter { letter | digit | "_" } ;
Number         = Integer | Float ;
Boolean        = "true" | "false" ;

4.4 Control Structures

If-Else

Conditional execution evaluates a boolean expression. If the condition is true, the if body executes; otherwise, the optional else body executes. Nested conditionals are supported through block statements. 

if (score >= 50) {
  result = 1;
} else {
  result = 0;
}

Loops: while and for

The while loop repeatedly executes while its condition remains true. The for loop provides structured initialization, condition, and update in one header. 

while (i < 5) {
  sum = sum + i;
  i = i + 1;
}

for (j = 0; j < 10; j = j + 1) {
  total = total + j;
}

4.5 Example Programs

Example 1: Arithmetic and Branching

int a = 8;
int b = 3;
int max;

if (a > b) {
  max = a;
} else {
  max = b;
}

Example 2: Factorial Using while

int n = 5;
int fact = 1;

while (n > 1) {
  fact = fact * n;
  n = n - 1;
}

Example 3: Function and for Loop

func int sumToN(int n) {
  int s = 0;
  int i;
  for (i = 1; i <= n; i = i + 1) {
    s = s + i;
  }
  return s;
}

int out;
out = sumToN(10);
Important concept: The language keeps syntax intentionally small and deterministic so parsing can be implemented via recursive descent with clear precedence handling.

5. Compiler Architecture Document

5.1 Phase-wise Breakdown

Phase Input Output Main Responsibility
Lexical Analysis Source code characters Token stream Groups characters into lexemes and emits typed tokens with line/column metadata.
Syntax Analysis Token stream Parse tree / AST Validates grammar structure and constructs hierarchical syntax representation.
Semantic Analysis AST + symbol environment Annotated AST + diagnostics Performs scope resolution, declaration checks, type checking, and control-flow validity checks.
Intermediate Code Generation Annotated AST Three-address code (IR) Transforms high-level constructs into low-level, linear, machine-independent operations.
Code Optimization IR Optimized IR Applies constant folding, dead code elimination, copy propagation, and algebraic simplification.
Target Code Generation Optimized IR Stack-machine style target code Maps IR operations into executable instruction sequence with labels and jumps.

5.3 Detailed Data Flow Explanation

The compiler starts by scanning source text and emitting a normalized token stream with exact source positions. Syntax analysis consumes tokens and builds an AST according to the language grammar. This AST captures hierarchical program structure while removing unnecessary concrete syntax details such as redundant punctuation nodes.

Semantic analysis then traverses the AST using a scope stack and symbol table. Every declaration introduces symbols; every usage is resolved to the nearest visible declaration. The analyzer attaches inferred or declared types to expressions and statements, verifies assignment compatibility, checks function return paths, and validates argument counts and parameter types in calls.

Intermediate code generation lowers AST nodes into three-address instructions such as temporary assignments, conditional jumps, labels, and call operations. This IR provides a stable boundary where optimization passes can operate without high-level grammar complexity. Optimization rewrites IR to reduce runtime cost and code size while preserving behavior.

Finally, the target code generator maps optimized IR into a stack-machine style assembly format with explicit control-flow labels. The output is suitable for an interpreter or virtual machine, and its deterministic instruction patterns simplify debugging and testing.

5.4 Sample IR Snippet

# Source: if (a > b) max = a; else max = b;
t1 = a > b
ifFalse t1 goto L_else
max = a
goto L_end
L_else:
max = b
L_end:

6. Team Reflection (Detailed Narrative)

6.1 Challenges Faced and Solutions

The most difficult challenge was designing a grammar that is expressive enough for functions, conditionals, and loops while still remaining parser-friendly for a recursive descent implementation. Our first grammar draft contained hidden left recursion inside expression productions and ambiguous alternatives around statement parsing. These issues caused backtracking loops and inconsistent parse trees in nested conditionals. We resolved this by separating precedence levels into dedicated non-terminals and by converting problematic statement rules into deterministic lookahead-based branches.

Another major challenge appeared in semantic analysis, particularly around scope handling and symbol shadowing. Initially, identifiers declared in inner blocks incorrectly replaced outer declarations globally due to a flat table implementation. This caused false redeclaration errors and incorrect type references. We replaced the flat table with a stack of scope frames and implemented nearest-scope-first lookup. This change stabilized name resolution and made shadowing behavior predictable for nested blocks.

Error reporting quality also required significant iteration. Early versions stopped at the first syntax or semantic failure, which made debugging user programs frustrating. We introduced phase-specific recovery strategies: token synchronization in parser checkpoints, and semantic pass continuation after non-fatal errors. With these improvements, users receive multiple actionable diagnostics in one run, including line positions, expected symbols, and recommended fixes.

In code generation, control-flow translation for if-else and loops produced jump label collisions because label IDs were reused in recursive contexts. This bug was subtle and only visible in nested structures. The team solved it by centralizing label allocation through a monotonic counter and adding unit tests for nested branches and nested loops. After this fix, generated code maintained proper control flow in all tested scenarios.

6.2 What We Learned About Compiler Design

The project made clear that compiler phases are conceptually distinct but practically interconnected. Decisions made in lexical conventions influence parser complexity; AST design determines how easy semantic checks and code generation become. We learned to define strong interfaces between phases, such as stable token types and typed AST nodes, to avoid cascading refactors.

We also learned that correctness and developer usability must be balanced. A technically correct parser that emits poor diagnostics still creates a weak user experience. Therefore, we treated diagnostics as a first-class feature. We added structured error objects carrying phase name, line, column, message, and hint, which improved both debugging and test verification.

A key insight from optimization work is that even small transformations require careful semantic guarantees. For example, constant folding appears simple, but folding expressions with division or mixed types must preserve language rules precisely. This taught us to pair every optimization rule with explicit preconditions and regression tests to ensure no behavior changes occur unexpectedly.

Finally, we gained practical understanding of intermediate representations. Converting high-level structures into three-address style operations clarified control flow and made optimization and target generation much cleaner. IR served as a unifying abstraction that reduced complexity in later stages and improved maintainability.

6.3 Future Improvements

With additional time, we would expand language features to include arrays, strings, and user-defined structures, along with stronger type inference for mixed numeric expressions. We would also add short-circuit evaluation in optimization and perform control-flow graph based passes such as loop-invariant code motion.

Another planned improvement is modular tooling support: a command-line mode with configurable flags, an interactive visualization mode that renders parse trees and symbol tables, and JSON output for integration with external IDE tools. This would make the compiler easier to evaluate in educational and automated grading contexts.

On testing, we would introduce differential testing against reference interpreters and increase fuzzing coverage for lexer/parser edge cases. We also intend to include a richer benchmark suite to measure optimization gains and verify that generated target code remains efficient as language features grow.

6.5 Closing Reflection

Completing a compiler end-to-end transformed abstract classroom concepts into concrete engineering practice. The team learned to treat each phase as both an isolated component and part of a larger pipeline contract. Through repeated debugging and redesign, we built confidence in language implementation, formal reasoning, and collaborative software construction. The final result is a robust educational compiler architecture that can be extended into a richer language platform in future iterations.
