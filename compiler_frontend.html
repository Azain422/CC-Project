Front-End Documentation for a Mini C-like Compiler

This document presents the design of the compiler front-end: lexical analysis, syntax analysis, and semantic analysis. The mini language supports variable declarations, assignment, arithmetic expressions, conditional statements, function definitions, and return statements.

1. Lexical Analyzer Design

DFA for Token Recognition (Inline SVG)

Transition Table

Current State Input Class Next State Action
S0 letter or _ ID Start lexeme buffer
S0 digit INT Start numeric literal
S0 operator char (+ - * / = ! < >) OP Emit operator token (check for multi-char operators)
S0 delimiter (; , ( ) { }) DELIM Emit delimiter token
ID letter, digit, _ ID Continue building identifier
ID other S0 Retract one char; classify as keyword or identifier

Token Categories

Keywords int, float, if, else, while, return, func
Identifiers Pattern: [A-Za-z_][A-Za-z0-9_]* (excluding reserved keywords)
Operators +, -, *, /, =, ==, !=, <, >, <=, >=
Literals Integer literals (0, 42, 105), float literals (3.14, 0.5)
Delimiters ; , ( ) { }

How Tokenization Works

The lexer performs a single left-to-right scan over source code. Whitespace and comments are skipped. For each next non-space character, the lexer enters an automaton path to consume the longest valid lexeme. If the lexeme matches a reserved word table, it is emitted as a keyword token; otherwise it is an identifier. Numeric lexemes are emitted as literal tokens, and punctuation/operator lexemes are emitted immediately. On any illegal character or malformed token pattern, the lexer reports a lexical error with precise position.

2. Parser Design

Context-Free Grammar (CFG)

Program      -> DeclList
DeclList     -> Decl DeclList | epsilon
Decl         -> VarDecl | FuncDecl | Stmt
VarDecl      -> Type id ';'
Type         -> int | float
FuncDecl     -> func id '(' ParamList ')' Block
ParamList    -> Param ParamTail | epsilon
ParamTail    -> ',' Param ParamTail | epsilon
Param        -> Type id
Block        -> '{' StmtList '}'
StmtList     -> Stmt StmtList | epsilon
Stmt         -> VarDecl
             | AssignStmt
             | IfStmt
             | ReturnStmt
             | Block
AssignStmt   -> id '=' Expr ';'
IfStmt       -> if '(' Expr ')' Stmt ElsePart
ElsePart     -> else Stmt | epsilon
ReturnStmt   -> return Expr ';'
Expr         -> Term ExprPrime
ExprPrime    -> '+' Term ExprPrime
             | '-' Term ExprPrime
             | epsilon
Term         -> Factor TermPrime
TermPrime    -> '*' Factor TermPrime
             | '/' Factor TermPrime
             | epsilon
Factor       -> id | number | '(' Expr ')'

Parsing Approach

The parser uses a Recursive Descent strategy aligned with an LL(1)-friendly grammar. Left recursion is removed and expression precedence is encoded using Expr/Term/Factor layers. Each non-terminal is implemented as a function that checks expected lookahead tokens and builds parse tree nodes. Syntax errors are reported with expected token sets and source line numbers.

Semantic Analysis Rules

Type checking: Each assignment and expression is validated for type consistency. For example, assigning a float expression to an int variable without explicit conversion triggers a type mismatch error. Operator compatibility is also enforced (arithmetic operators require numeric operands).

Scope resolution: The analyzer maintains a scope stack. On entering a block or function, a new scope frame is pushed; on exit it is popped. Identifier lookup starts in the innermost scope and walks outward, enabling legal shadowing while still preserving global accessibility.

Semantic error handling: The analyzer reports undefined identifiers, redeclaration in the same scope, function call argument count/type mismatches, invalid return types, and use-before-initialization. Errors include source line references and continue in recovery mode to collect multiple diagnostics in one pass.

Semantic passes are executed after successful parsing so type and scope checks operate on a structurally valid parse tree or AST.
